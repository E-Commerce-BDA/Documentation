## 2. Distribution

The package is distributed as a GitHub Release tarball:

```json
{
  "@ecom/contracts": "https://github.com/E-Commerce-BDA/ecom-contracts/releases/download/v1.9.0/ecom-contracts-1.9.0.tgz"
}
```

Why not GitHub Packages: GitHub Packages requires the npm scope to match the
repository owner (`E-Commerce-BDA`), which would force the package name to
change from `@ecom/contracts`. The release tarball keeps the required name,
is immutable by tag, and needs no registry scope.

`ecom-infra` pins the local tarball by path (`file:../ecom-contracts/ecom-contracts-1.8.0.tgz`)
because it runs from the same workspace; every other consumer pins the release
URL. Both are exact pins — a `^` range is a review failure.

## 3. Release checklist

Every step is required; steps 5–6 are the two a human has to approve.

| # | Step | Command / artefact |
|---|---|---|
| 1 | Pre-flight gates green on the branch | `pnpm typecheck && pnpm test && pnpm build` |
| 2 | Version bumped and CHANGELOG entry written (newest first) | `package.json` `version`, `CHANGELOG.md` |
| 3 | Tarball built locally and inspected | `pnpm pack` → `ecom-contracts-<version>.tgz`; the tarball must contain `dist/schemas/*` for every schema touched |
| 4 | The new tarball installed into at least one consumer | `ecom-infra`: update the `file:` pin, `pnpm install --ignore-workspace`, `pnpm verify` |
| 5 | **Consumer suites green on the new pin** (human approves) | `cms-svc`, plus every service that consumes the changed schema: `pnpm test && pnpm test:e2e`. A MINOR release must not require a single consumer code change; if it does, it was not MINOR |
| 6 | **Tag approved and pushed** (human approves) | tag `v<version>`; the tag must equal `v` + `package.json.version`. CI re-runs the gates and refuses a mismatch |
| 7 | Release asset published | GitHub Actions runs `pnpm pack` and attaches `ecom-contracts-<version>.tgz` to the release |
| 8 | Consumers repinned | each service's `package.json` moves to the new exact URL, `pnpm-lock.yaml` re-resolves, one commit per repo |

Steps 3–5 exist because a tarball can be produced that passes `tsc` and still
breaks a consumer at runtime: `1.8.0` is a good example — adding
`src/schemas/queues.ts` needed a barrel export in `src/index.ts`, and a missing
export fails only at import time in the consumer, never in this repo's suite.

No registry publish, no `latest`, no floating ranges.

**Where the train stands.** Repins are per-consumer, because a repin costs a
four-suite re-verification and only some consumers read the new shape.

| Pin | Consumers | Why they are there |
|---|---|---|
| `1.9.0` | `catalog-svc`, `search-svc` (vendored in-repo), `ecom-messaging` (devDep) | `cat-008` and `srch-002` must parse `product.imported` with `variants[]` |
| `1.8.0` | `auth-svc`, `cart-svc`, `cms-svc`, `order-svc`, `ecom-infra` | none of them reads a `product.*` payload. `cart-svc` deliberately stays here even though its `@ecom/messaging 0.3.0` declares a higher floor — see the pin-mismatch note in §10 |
| `1.7.0` | `frontend/storefront` | it imports CMS section/media types that have not changed since 1.7.0; `ec-005` is the task that moves the stragglers in one train |

**The strict-schema adoption order is a rule, not a preference.** Every event
payload schema is `.strict()`, so an added field is *not* backward compatible at
runtime: a producer that starts emitting `variants` makes any consumer still
pinned at `≤ 1.8.0` fail `parseEventPayload` and dead-letter the record with
`invalid-payload`. `1.9.0` is therefore a MINOR by shape and an **ordered
rollout** by behaviour:

1. publish `1.9.0` (additive; nothing emits the new field yet);
2. repin every consumer that reads the changed topic — for `variants` that is
   `search-svc` and `catalog-svc`, both in the same wave;
3. only then let a producer, fixture or importer emit the new field.

Steps 1–2 are inert on their own; step 3 is the one that can break a lagging
consumer. Doing 3 first is how a replay window silently becomes a DLQ full of
records that were valid when they were sent.

The `1.8.0` → `1.7.0` split above is the other half of the same argument: a
MINOR that only *adds* schemas (`queues.ts`, the job payloads) nothing imports
yet is inert, so `ec-005` can move those consumers whenever it is convenient.

## 4. Semver rules

### MAJOR

- Remove or rename a required field.
- Change a field's type or meaning.
- Remove an enum value or change its semantics.
- Change an endpoint path, response envelope, event name, or job payload shape
  in a way that breaks an existing consumer.
- **Rename or remove a queue or topic name** (`TASK_QUEUES`, `EVENT_TOPICS`),
  because the name is the contract with the broker.

### MINOR

- Add an optional field.
- Add a section type, event type, job type, or schema export.
- Add an enum value when consumers can safely ignore unknown values.
- Add a settings key to a type's allowlist.
- **Add a queue or topic to a registry** — the new entry is inert until
  something produces to it.

### PATCH

- Docs, tests, comments, and internal refactors with no runtime shape change.

## 5. Consumer rules

- Pin exact versions; never `^` or `latest`.
- A MAJOR upgrade requires every consumer to re-pin in the same release train
  (see §9 for the 2.0.0 train).
- `null` is never a valid override; omit the key to inherit.
- Contract changes that affect the storefront resolver require a storefront
  test update in the same release train.
- A consumer never re-derives a contract locally. If a shape is missing, add it
  here in a MINOR release instead.

## 7. The 1.3.0 surface (envelope transition)

`1.3.0` introduced the canonical envelope without a flag day, and it is still the
shape every producer writes:

| Field | 1.3.0 status | 2.0.0 status |
|---|---|---|
| `type` | optional, canonical event name **and** Kafka topic | **required** |
| `version` | optional, defaults to `1` in `readEventEnvelope()` | **required** |
| `idempotencyKey` | optional, defaults to `id` | **required** |
| `topic` | legacy-optional | **removed** |
| `eventType` | legacy-optional | **removed** |
| `id`, `timestamp`, `producer`, `payload` | required | required |

Rules that hold for the whole window:

- At least one of `type`, `topic`, `eventType` must be present.
- When `type` is present, all three must agree — dual-write drift is a schema
  error, so a new producer fails fast instead of publishing on the wrong topic.
- When `type` is absent, the legacy CMS mismatch is still accepted; those
  messages keep parsing.
- `readEventEnvelope()` normalizes both shapes to
  `{id, type, version, timestamp, producer, idempotencyKey, payload}`; consumers
  never branch on which field the producer used.
- `canonicalEventEnvelopeSchema` already rejects everything in the 2.0.0 column
  of the table, so a producer can be 2.0.0-ready today.

## 8. The 1.9.0 surface (current, cumulative)

**Added by `1.9.0`** (`cat-008` needed it — an import that carries a variant
matrix had nowhere to put it):

- `productVariantRefSchema` (`.strict()`): `id?`, `sku: 1..64`, `price:
  number|string`, `effectivePrice?: number|string`, `stock?: non-negative int`,
  `imageUrl?: imageRef`, `isActive?: boolean`.
- `productImportedPayloadSchema.variants?: ProductVariantRef[]` — optional, so a
  payload without it still parses.
- **Not** added to `productUpdatedPayloadSchema`. The asymmetry is deliberate:
  catalog's own `product.updated` emitter knows its variants locally, so only the
  external-import edge needs the array. Adding it to both would double the
  surface for no consumer.

**Everything below is cumulative from 1.0.0–1.8.0:**

- Shared primitives (keys, UUIDs, hex colours, internal paths, image refs, ISO dates).
- CTA schema with `max(3)`, CMS section types, per-type content and settings
  schemas, `SECTION_CATALOG`, section list/reorder responses.
- Theme, navigation, pages, blogs, media (`visibility`), page settings.
- `events.ts`: envelope + one payload schema per topic (11).
- `topics.ts`: `EVENT_TOPICS`, `eventPayloadSchemas`, `parseEventPayload()`,
  `parseEventEnvelope()`, `dlqTopicName()`, `isEventTopic()`.
- `jobs.ts`: `sendEmailJobSchema`, `processImportRowJobSchema`,
  `resizeImageJobSchema` — all strict, all with a bounded payload.
- `queues.ts`: `TASK_QUEUES` (`notify-send-email`, `import-process-row`,
  `media-resize-image`), `TASK_QUEUE_NAMES`, `TASK_DLQ_NAMES`,
  `taskQueueNameSchema`, `isTaskQueue()`.
- `search.ts`: search DTOs, query + suggest schemas, ingestion, stats.

Queue names are hyphenated because SQS accepts only alphanumerics, hyphens and
underscores (a dot is legal only as a trailing `.fifo`). A rename has to land in
three places at once — `queues.ts`, `ecom-infra/localstack/init/ready.d/10-sqs-queues.sh`,
`ecom-infra/aws/sqs.tf` — which is why §4 makes it a MAJOR change.

## 9. The 2.0.0 surface (planned release train)

`2.0.0` deletes the legacy envelope, so it is the only change in this document
that cannot be rolled out one consumer at a time.

| Step | Owner | Gate |
|---|---|---|
| 1. Every producer dual-writes `type` + `topic` + `eventType` and emits `version` and `idempotencyKey` | auth, cart, catalog, order, cms, analytics | an event captured from each producer validates against `canonicalEventEnvelopeSchema` |
| 2. Every consumer reads through `readEventEnvelope()` | all consumers | no consumer touches `envelope.topic` or `envelope.eventType` directly |
| 3. `2.0.0` published: `topic`/`eventType` removed, `canonicalEventEnvelopeSchema` becomes `eventEnvelopeSchema` | contracts | consumers repinned and their suites green (§3 step 5) |
| 4. Old records still in Kafka are drained or allowed to expire | operations | retention window (3d/7d/30d per topic) has passed |
| 5. Legacy fields deleted from the docs and from `1.Architecture.md §6.2` | Documentation | `grep -r "eventType" Documentation/` returns only the 1.3.0 section of this file |

Until step 3 lands every new schema is **additive**, and the pins stay mixed
(§3). A MAJOR is the one change that cannot be rolled out per consumer, which is
exactly why everything since `1.3.0` has been MINOR.

**Step 1 is already satisfied by every producer that exists.** Since au-004 / ca-008,
`auth-svc` and `cart-svc` build every envelope through `@ecom/messaging`'s
`buildEventEnvelope()`, which dual-writes `type` + `topic` + `eventType`, sets `version: 1`
and `idempotencyKey = id`, and re-validates the result against `eventEnvelopeSchema` before
the outbox row is written. Since cat-007 / ord-011 / cms-005 the same is true of
`catalog-svc`, `order-svc` and `cms-svc` — all five producers now go through the package, and
none of them can publish a non-canonical envelope. `analytics-svc` publishes
`cart.abandoned` / `page.viewed` by design once `anl-004` builds it, and it will adopt the
package then.

## 10. The second versioned package: `@ecom/messaging`

`@ecom/contracts` describes shapes; it cannot contain the outbox/relay mechanism
(that needs `pg`, `mongodb`, `kafkajs` and Nest). The mechanism is therefore its own package.

| Item | Value |
|---|---|
| Repo | `E-Commerce-BDA/ecom-messaging` (local path `../ecom-messaging`) |
| Package | `@ecom/messaging` |
| Current version | `0.5.0` |
| Module format | ESM + `.d.ts`; subpaths `.` (framework-free), `./nest`, `./nest/consumer`, `./nest/outbox`, `./nest/tasks`, `./tasks` |
| Runtime peer | `@ecom/contracts >=1.9.0 <2` (required); `kafkajs`, `@nestjs/common`, `@nestjs/mongoose`, `@nestjs/microservices` and `@aws-sdk/client-sqs` (optional — only the transport each one belongs to needs them). **No** `pg`, `mongodb` or `mongoose` import: both stores are typed structurally (`PoolLike`, `MongoSessionLike`, `MongoCollectionLike`) |
| Consumer pin | committed tarball + `file:` pin (`pnpm install --ignore-workspace`) |
| Producer adopters | all five — `auth-svc` (`user.registered`, au-004), `cart-svc` (`cart.updated`, ca-008), `catalog-svc` (`product.updated` / `category.updated`, cat-007), `order-svc` (`order.created` / `order.status.updated`, ord-011), `cms-svc` (`cms.updated` / `blog.updated`, cms-005) |
| Consumer adopters | all three that have one — `search-svc` (4 topics, srch-002, on `0.5.0` since srch-004), `cart-svc` (`order.created`, ca-009, `0.3.0`), `catalog-svc` (`order.created` + `product.imported`, cat-008, `0.3.0`) |

| `0.4.0` | MINOR (additive) | The task half, for `cms-006`: `TaskQueuePort`/`TaskWorkerPort`, `SqsTaskQueue`, `SqsTaskWorker`, `SqsQueueUrls`, `createSqsTaskModule`; optional peer `@aws-sdk/client-sqs`; narrow `./nest/outbox` and `./nest/tasks` entries so a producer does not load the Kafka transport |
| `0.5.0` | MINOR (additive, one removal) | The ladder is bounded by the session (`srch-004`): `DEFAULT_SESSION_TIMEOUT_MS` 45s + `DEFAULT_HEARTBEAT_INTERVAL_MS` 3s set explicitly on the strategy with a boot guard, and `KafkaEventHandler` option `retryBudgetMs` truncating the ladder. `./nest/consumer` and `./tasks` added; the root barrel no longer re-exports the SQS implementations, which an optional peer must not make unreachable (`test/entry-points.spec.ts`). `search-svc` repinned; cart and catalog stay on `0.3.0` |

**The 0.5.0 surface (the bounded consumer):**

- `createKafkaConsumerStrategy({ sessionTimeoutMs, heartbeatIntervalMs })` — both are
  now passed to kafkajs explicitly. Before this the package set neither, so a
  library default owned a production contract: the 31s ladder was larger than the
  30s session, and a member evicted mid-retry could neither dead-letter nor commit.
  A heartbeat at or above the session timeout is rejected at boot.
- `KafkaEventHandler({ retryBudgetMs })` — an upper bound on the **total sleep** of
  the ladder. The ladder is truncated at construction to the longest leading run
  that fits, `maxRetries` follows it, the first delay is always kept, and the cut is
  warned at boot. Omitted, the ladder runs exactly as configured.
- A service that consumes but never enqueues imports `@ecom/messaging/nest/consumer`
  (and the root barrel for the framework-free half); a service that enqueues imports
  `./nest/tasks`. `test/entry-points.spec.ts` walks the source graph and fails if an
  entry point reaches `@aws-sdk/client-sqs` it does not need.

**The 0.3.0 surface (the consumer half):**

- `createKafkaConsumerStrategy({ brokers, clientId, groupId })` (`./nest`) — a
  `ServerKafka` with `postfixId: ''`, `autoCommit: false`, a deserializer that
  hands the handler the raw JSON string and `parser.keepBinary`. Each setting was
  read out of `@nestjs/microservices` 12.3.2 rather than assumed; the three
  silent failure modes are pinned by tests.
- `KafkaEventHandler.run(ctx, topic, raw, handle)` (`./nest`) — the whole
  protocol in one place: parse, retry `1/2/4/8/16s`, dead-letter, then commit,
  in the order **side effect → counter → offset**. Handlers return
  `{ kind: 'applied' | 'duplicate' | 'ignored' | 'invalid' }`; an optional
  `translateError(err) => reason | null` turns a service-specific terminal error
  into an immediate dead letter. `KafkaConsumerStalledError` is the only thing
  `run` throws, and only when the dead-letter write itself failed.
  From `0.5.0` the ladder is capped by `retryBudgetMs`, and 31s is no longer what
  an unconfigured consumer sleeps.
- `ProcessedEventsStore({ schema }).claim(client, eventId, topic)` — the
  `INSERT … ON CONFLICT (event_id) DO NOTHING RETURNING event_id` claim, taking
  the caller's client so the claim and the domain write are one transaction.
- `KafkaDlqPublisher` — lazy shared producer, `dlqTopicNameFor` from the registry
  with a `${topic}.dlq` fallback, `close()` for shutdown.
- `KafkaLagSampler` — standalone admin client (no dependency on the Nest
  strategy), `fetchTopicOffsets − fetchOffsets({ groupId })`, `-1` means "never
  committed", unref'd 15 s timer.
- `ConsumerMetrics` — the nine counters plus `recordCommit()` / `lastCommit()`.
- `.` stays framework-free: `run()` accepts a structural context (anything with
  `getMessage` / `getPartition` / `getConsumer`), so the package imports no Nest
  type outside `./nest`.

**The 0.2.0 surface:**

- `OutboxStorePort<Ctx = Queryable>` — `write(ctx, input)`, `claimBatch`, `markPublished`,
  `markFailed`, `tryAcquireRelayLock`, `initialize?()`. The default `Ctx` is what kept cart's
  and auth's call sites source-compatible through the generic rewrite.
- `PostgresOutboxStore` — `FOR UPDATE SKIP LOCKED` + `locked_until`, `pg_try_advisory_lock`
  on the **unquoted** `schema.table` string (so the lock namespace did not change for auth and
  cart), identifiers quoted as `"schema"."table"`.
- `MongoOutboxStore` — repeated atomic `findOneAndUpdate` claiming, a lease document in
  `<collection>_locks`, indexes created by `initialize()`. There is no Mongo migration file;
  index creation is part of the store's contract.
- `OutboxRelay` and `buildEventEnvelope` are shared by both stores. The retry ladder
  (`attempts + 1`, `min(2^attempts, 60)s`, park at 5), the mark-published-after-ack rule and
  per-aggregate ordering are defined once, in the relay.
- Nest: `createOutboxModule` (Postgres) and `createMongoOutboxModule` (Mongo) register the same
  `OUTBOX_PUBLISHER` / `OUTBOX_RELAY` / `OutboxLifecycle` providers. The `enabled` flag
  (`DISABLE_OUTBOX_RELAY`) is read at module-declaration time, so an e2e config sets it in
  `env`, and a live spec overrides the `OUTBOX_PUBLISHER` provider instead.

**Version rules while pre-1.0:**

- Breaking shape change → MINOR bump (`0.2.0` → `0.3.0`). Under `0.x` a MINOR is the
  breaking-change signal, so PATCH is reserved for fixes that keep every export usable.
- Fix or additive export → PATCH.
- **`1.0.0` is overdue rather than blocked.** The original trigger was "the third adopter
  lands"; `ord-011` was the third and `cat-007` / `cms-005` followed in the same wave, so five
  adopters now run it. `0.2.0` was still the right release for *that* change, because the
  release itself is the breaking one (generic port, second store) and `1.0.0` should mean
  "these shapes are frozen", not "the biggest change just landed". `0.3.0` did not move that
  needle either: it is additive — five new exports and one optional peer — and the consumer
  surface was meant to be the last planned addition. It was not. `0.4.0` (tasks) and `0.5.0`
  (bounded ladder, narrow entries) both followed, so the sentence "the next change should be
  the freeze" has now been wrong twice and is withdrawn: `1.0.0` is a decision to stop adding
  surfaces, and it needs the `analytics-svc` consumer plus an explicit freeze list to mean
  anything.
- **Known pin mismatch (cart-svc).** `cart-svc` pins `@ecom/messaging 0.3.0` against
  `@ecom/contracts 1.8.0` while the package declares `>=1.9.0 <2`. `ca-009` kept cart on
  `1.8.0` deliberately — its only route is `order.created`, which parses no `product.*`
  payload and therefore touches nothing `1.9.0` added — and pnpm accepts the pair (it records
  the `1.8.0` instance as the resolved peer). It is a floor that is higher than cart needs,
  not a runtime break: every cart suite is green on it. It closes the moment cart repins
  contracts for any other reason; there is no separate task for it because repinning is
  additive.
- Consumers pin the exact tarball. Bumping the package means: `pnpm pack` in
  `ecom-messaging`, commit the `.tgz`, repin **every** consumer, re-run its full suite. Two
  package versions in one monorepo is how a stale `file:` tarball happens — and it did happen
  once during this wave (a service kept a copy predating the `findOneAndUpdate` return-shape
  fix).

The package validates against **the consumer's own copy of `@ecom/contracts`**, so a
contracts MINOR is picked up by repinning contracts alone — no messaging release needed,
as long as the peer range still matches.
