# 0. Project Overview

> E-Commerce Platform — Learning-Focused, Event-Driven, CMS-Driven Storefront
> Status: Draft | Last Updated: 2026-09-03
> Repo Model: **Polyrepo (12 repos, 1 deployable per repo)** | Scale: **Learning-based, NOT traffic-scale** | Contracts: **`@ecom/contracts` versioned pnpm package — semver (see `8.Versioning.md`)**

---

## 1. Project Vision

Build a production-shaped, learning-focused e-commerce platform with three major surfaces:

1. **Storefront (customer-facing)** — a Next.js application with SSR/SEO-optimized pages: homepage, product listing, product detail, cart, checkout, account, blogs, brands.
2. **Admin Panel / CMS (merchant-facing)** — a separate Next.js application where the store owner controls content, products, navigation, and visual customization without touching code. Nearly every visual aspect of the storefront is configurable.
3. **Backend (microservices)** — NestJS services communicating through an **event bus abstraction (`IEventBus`)**, fronted by Nginx as a reverse proxy / API gateway, backed by PostgreSQL + MongoDB + Redis.

The project exists to *learn* real-world e-commerce engineering: event-driven architecture, distributed systems, CMS design, analytics/tracking, and cost-conscious AWS deployment — all within a realistic budget.

> **Operating principles (2026-09-03):** **(1) Polyrepo** — 12 separate git repos (storefront-ui, admin-app, ecom-contracts, 9 services + ecom-infra); one pipeline and one deploy per repo; shared code only via versioned `@ecom/contracts`. **(2) Learning-based, NOT traffic-scale** — single EC2 + 1 Kafka broker locally is intentional for learning; traffic-scale (K8s/MSK/ElastiCache) is a documented evolution path, not v1. **(3) Dual transport** — `TRANSPORT=kafka` locally (self-hosted KRaft on EC2, $0), `TRANSPORT=sqs` on AWS (SNS→SQS, ~$0–2/mo); services depend only on `IEventBus`, never on a concrete transport.

## 4. Tech Stack Decisions

### 4.1 Decisions Locked (2026-09-03)
| Decision | Choice | Rationale |
|---|---|---|
| Frontend | **Next.js 16 + React 19** (App Router, TypeScript) — storefront **and** separate admin app | SSR for SEO; one ecosystem; admin isolation for cleaner RBAC and deploys; Next 16 requires React 19 |
| Backend | Node.js + **NestJS** microservices | One TypeScript language across repos; structured modules; mature Kafka/ORM support |
| Messaging | **Event bus abstraction `IEventBus`** — **Kafka (KRaft) locally / SNS→SQS on AWS** via `TRANSPORT=kafka\|sqs` | Learn Kafka locally; avoid MSK cost on AWS (~$460+/mo min); SQS is ~$0–2/mo at our volume; same envelope via `@ecom/contracts` |
| Contracts | **Polyrepo + `@ecom/contracts` pnpm package** (versioned, semver) | One deployable per repo; breaking event/DTO changes use MAJOR + dual-publish window + CHANGELOG (see `8.Versioning.md`) |
| Repo model | **12 repos**: `storefront-ui`, `admin-app`, `ecom-contracts`, 9 services (`auth/catalog/cart/order/cms/analytics/import/notify/search`), `ecom-infra` | Independent pipelines/deploys; ownership clear; traffic-scale shape is identical (see §11) |
| Learning scale | **NOT traffic-scale in v1** — single EC2 + 1 broker + Atlas M0 + Redis on-box intentionally | Optimizes for learning clarity; hardening (K8s/MSK/ElastiCache/schema registry) is an evolution path, not v1 |
| Databases | **PostgreSQL** (core relational data) + **MongoDB** (CMS/catalog flexibility) | Mongo Atlas free M0 tier for CMS documents, flexible product attributes; Postgres for orders/inventory integrity |
| Cache | **Redis** | Caching (catalog, sessions), rate limiting, rate-limit + consumer coordination |
| Proxy/Gateway | **Nginx** (learning) → ALB/API Gateway (traffic-scale) | Reverse proxy, static serving, TLS termination, routing to services |
| Deployment | **Iterative deploys: one image per repo → ECR/GHCR → `ecom-infra` pins tags in `VERSIONS.env`** | Small diffs, fast rollback, prod issues spotted immediately; rollback = revert one tag |
| Admin panel | **Separate Next.js app** (`/admin` domain) | Clear separation of concerns, isolated builds/deploys, stricter auth |

### 4.2 Core Libraries (confirmed in `2.Tech-Stack.md`)
- **Next.js 16 + React 19**: App Router, Server Components, ISR for catalog pages; `next/font` Outfit+Fraunces.
- **NestJS 10 + Prisma 5**: `@nestjs/microservices` + Prisma as primary ORM (see `2.Tech-Stack.md` for rationale).
- **Event bus**: `kafkajs` via `KafkaBus` when `TRANSPORT=kafka` (local); `@aws-sdk/client-sns` + `@aws-sdk/client-sqs` via `SnsSqsBus` when `TRANSPORT=sqs` (AWS); both behind `IEventBus` (`@ecom/contracts` envelope).
- **Contracts**: `@ecom/contracts` — event envelopes + Zod `ctas[].max(3)` + DTOs + error codes (pinned version, no `^`).
- **Redis**: `ioredis` + `@nestjs/cache-manager`.
- **PostgreSQL**: `postgres:16`; **MongoDB**: Atlas M0 (free); **Redis**: `redis:7` container on EC2 (local) / ElastiCache (traffic-scale).

### 4.3 Nginx Responsibilities
- Route `storefront.example.com` → Next.js storefront (port 3000).
- Route `admin.example.com` → Next.js admin (port 3001).
- Route `api.example.com/api/v1/*` → NestJS services by path prefix (e.g. `/auth`, `/catalog`, `/cart`, `/order`, `/cms`, `/search`).
- TLS termination (Let's Encrypt), gzip, static caching, rate limiting per IP.

## 7. Key Event-Driven Flows (Topics — transport-agnostic via `IEventBus`)

Contracts in `@ecom/contracts` (`src/events/`): envelope `{id,type,version,timestamp,producer,idempotencyKey,payload}` is identical on both transports. Local: Kafka topics (see `1.Architecture.md §6`). AWS: SNS topics → per-consumer SQS queues (see `1.Architecture.md §6.5`).

| Event | Producer(s) | Consumers | Purpose |
|---|---|---|---|
| `cart.updated` | cart-svc | analytics-svc, notify-svc | Track cart activity; feed abandoned-cart detection |
| `cart.abandoned` | analytics-svc (detector) | notify-svc | Trigger reminder email after inactivity window (e.g. 24h) |
| `order.created` | order-svc | catalog-svc (stock), analytics-svc, notify-svc | Stock decrement, analytics, confirmation email |
| `order.status.updated` | order-svc | notify-svc, storefront (via API) | Shipment/status updates |
| `product.imported` | import-svc | catalog-svc, cms-svc, search-svc | Ingest imported products; refresh CMS caches + search index |
| `product.updated` | catalog-svc | search-svc | Admin product edits keep the search index fresh |
| `category.updated` | catalog-svc | search-svc, cms-svc | Category renames/visibility → search + navbar |
| `blog.updated` | cms-svc | search-svc | Blog create/publish/edit → search index |
| `page.viewed` | storefront (producer) | analytics-svc | Anonymous + logged-in page views, exit tracking |
| `user.registered` | auth-svc | analytics-svc, notify-svc | Welcome email, cohort analytics |

**Abandoned cart flow (v1):** storefront emits `cart.updated` → cart-svc persists cart with `updated_at` → analytics-svc runs a scheduled consumer that marks carts idle > X hours → publishes `cart.abandoned` → notify-svc sends email. (Implementation details in `1.Architecture.md`.)

**Exit tracking (v1):** storefront fires `page.viewed` with `{userId?, sessionId, page, referrer, timestamp, device}` and a `page.left` heartbeat on `beforeunload`/`visibilitychange` → analytics-svc builds "where users leave" reports.

## 11. Budget & Deployment Strategy

### 11.1 AWS Free Plan — Credit Model (from 2025-07-15): up to $200 for 6 months

Joining an Organization/Control Tower expires credits immediately — do not do this on the learning account. Free Plan gives credits across **200+ services** + **30+ Always Free** services with monthly limits.

| RDS Postgres db.t4g.micro (~20GB) | Managed Postgres (Free Plan credits cover this; legacy 12-mo free tier if account older) | ~$12 |

| Let's Encrypt | TLS certs | $0 |

Guardrails: billing alerts at 50%/25%/10% credits + 15/7/2-day expiry mails (AWS sends these); stop EC2 when idle; keep an S3 snapshot export of RDS for the 90-day grace restore path; set AWS Budgets alerts on first day.

### 11.2 Architecture Decisions for Cost
- One EC2 box (learning-scale, NOT traffic-scale): Docker Compose runs all NestJS services + Redis + Nginx + two Next.js apps; **Kafka runs only on the `local` compose profile** (`TRANSPORT=kafka`), omitted on AWS (`TRANSPORT=sqs`).
- No MSK (managed Kafka ~$460+/mo min), no ECS Fargate, no ElastiCache in v1 — all self-hosted/on-box to stay inside credits; traffic-scale evolution is K8s/ECS + ElastiCache + MSK 3-broker + read replicas (no repo-shape change, see §11.4).
- RDS Postgres (managed) rather than Postgres on EC2 — one managed component for reliability.
- Images on S3, served via Nginx/CDN.

### 11.3 Iterative Deploy Pipeline (learn by shipping small)
Per-repo pipeline (12 repos): `main` push → `lint → test → build image → push ECR/GHCR → deploy only that service` (ECS rolling or `compose pull <svc> && up -d <svc>` from `ecom-infra`'s `VERSIONS.env` which pins each image tag immutably). Small diffs spot prod issues immediately; rollback = revert one tag in `VERSIONS.env` + redeploy. Observability minimum: `GET /health` + `/health/ready` per service, `x-request-id` propagation, CloudWatch Logs + alarms (5xx, P99, queue age/consumer lag, billing).

### 11.4 Traffic-Scale Evolution (not v1, no repo-shape change)

| Layer | Learning (v1 now) | Traffic-scale (later) | Files affected |
|---|---|---|---|
| Orchestration | `ecom-infra/docker-compose.yml` on 1 EC2 | K8s (`infra-k8s/` Terraform) — HPA, rollingUpdate, PDB | New `infra-k8s/` manifests; per-svc `Dockerfile` non-root + `HEALTHCHECK` |
| Kafka | 1 KRaft broker, no registry | MSK 3 brokers / Confluent + Schema Registry | `ecom-contracts/src/events/`, `src/messaging/kafka-bus.ts` + registry client |
| Data | RDS single, Atlas M0, Redis on-box | RDS Multi-AZ + read replicas, Atlas M10+, ElastiCache Cluster | `prisma/schema.prisma` read/write split, Redis cluster mode |
| Gateway | Nginx | ALB + API Gateway / Kong + mTLS (replaces `x-service-key`) | `nginx.conf` → gateway routes; `service-key.guard.ts` → mTLS guard |
| Observability | JSON logs + health | OTel traces + Prometheus/Grafana + PagerDuty; SLOs | `src/main.ts` OTel SDK, dashboards |

## 13. Risks & Constraints

| Risk | Mitigation |
|---|---|
| Single-broker Kafka on t3.micro = no HA, limited RAM (learning-scale intentionally) | Acceptable for learning; KRaft mode (no Zookeeper) saves ~250MB; traffic-scale uses MSK 3 brokers — no repo change needed |
| t3.micro (2 vCPU / 1GB RAM) is tight for 9 services + Kafka + Redis + 2 Next.js | Kafka only on local profile (omitted on AWS with `TRANSPORT=sqs`); tune Node heap; credits buffer for t3.small burst |
| Free Plan ends after 6 months or credits exhausted → account auto-closes | Keep costs ~$20/mo (~$120/6mo inside $200); set Budgets + billing alerts 50/25/10% + 15/7/2-day mails; S3 snapshot of RDS before month 6 for 90-day grace restore; never join Organization/Control Tower (expires credits immediately) |
| MongoDB Atlas M0 limits (512MB, no backups) | Only CMS documents; Postgres remains source of truth for critical data |
| Guest cart persistence across devices | Session-scoped carts v1; merge on login |
| CMS settings explosion → slow storefront | Redis caching with invalidation on `cms.updated` events (transport-agnostic via `IEventBus`) |
| Events lost on restart (Kafka single broker, no replication / SQS deleted on consume) | Consumer idempotency design (events carry idempotency keys); on AWS use 14d SQS retention + optional S3 archive for manual replay (no log replay like Kafka) |
| Dual transport drift (Kafka vs SNS→SQS semantics differ) | Envelope identical (`@ecom/contracts`); `TRANSPORT` selects `KafkaBus` vs `SnsSqsBus`; FIFO queues preserve per-cart order, Standard for `page.viewed`; always long-poll 20s + batch 10 |
