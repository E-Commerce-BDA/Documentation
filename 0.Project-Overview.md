# 0. Project Overview

> E-Commerce Platform — Learning-Focused, Event-Driven, CMS-Driven Storefront
> Status: Draft | Last Updated: 2026-08-15

---

## 1. Project Vision

Build a production-shaped, learning-focused e-commerce platform with three major surfaces:

1. **Storefront (customer-facing)** — a Next.js application with SSR/SEO-optimized pages: homepage, product listing, product detail, cart, checkout, account, blogs, brands.
2. **Admin Panel / CMS (merchant-facing)** — a separate Next.js application where the store owner controls content, products, navigation, and visual customization without touching code. Nearly every visual aspect of the storefront is configurable.
3. **Backend (microservices)** — NestJS services communicating through Apache Kafka events, fronted by Nginx as a reverse proxy / API gateway, backed by PostgreSQL + MongoDB + Redis.

The project exists to *learn* real-world e-commerce engineering: event-driven architecture, distributed systems, CMS design, analytics/tracking, and cost-conscious AWS deployment — all within a realistic budget.

## 2. Goals

### 2.1 Learning Goals
| Goal | How this project covers it |
|---|---|
| Microservices architecture | Multiple NestJS services, each independently deployable |
| Event-driven design | Apache Kafka as the nervous system: orders, carts, analytics, imports |
| SSR/SEO for e-commerce | Next.js App Router with Server Components + ISR |
| CMS design | Schema-driven sections, global vs per-section settings, JSONB settings |
| Real-time analytics/tracking | Page-view events, exit tracking, abandoned-cart detection pipelines |
| DevOps on AWS | EC2 self-hosting, Docker Compose, Nginx, RDS, S3, SSL, cost management |
| Multi-database modeling | Relational (Postgres) vs document (MongoDB) trade-offs |
| API design | REST per service, contract-first events, versioned endpoints |

### 2.2 Product Goals
- A fully functional storefront: browse → compare → wishlist → cart → checkout → order.
- A CMS that can restyle the storefront (colors, ratios, layouts, photo treatment) with zero code deploys.
- Product import from CSV/JSON in v1; Shopify/BigCommerce/Odoo imports in the future.
- Behavioral insights: abandoned carts, exit pages, page-view funnels.

## 4. Tech Stack Decisions

### 4.1 Decisions Locked (2026-08-15)
| Decision | Choice | Rationale |
|---|---|---|
| Frontend | Next.js (App Router, TypeScript) — storefront **and** separate admin app | SSR for SEO; one ecosystem; admin isolation for cleaner RBAC and deploys |
| Backend | Node.js + **NestJS** microservices | One TypeScript language across the whole repo; structured modules; mature Kafka/ORM support |
| Messaging | **Apache Kafka** (event-driven from day 1) | Orders, carts, analytics, imports flow as events from the start |
| Databases | **PostgreSQL** (core relational data) + **MongoDB** (CMS/catalog flexibility) | Mongo Atlas free M0 tier for CMS documents, flexible product attributes; Postgres for orders/inventory integrity |
| Cache | **Redis** | Caching (catalog, sessions), rate limiting, rate-limit + consumer coordination |
| Proxy/Gateway | **Nginx** | Reverse proxy, static serving, TLS termination, routing to services |
| Deployment | **AWS EC2 self-managed** (Docker Compose) + RDS Postgres + Atlas Mongo | Cheapest within budget; best ops learning |
| Admin panel | **Separate Next.js app** (`/admin` domain) | Clear separation of concerns, isolated builds/deploys, stricter auth |

### 4.2 Core Libraries (initial selections, confirmed in DOCS/2.Tech-Stack.md)
- **Next.js**: App Router, Server Components, ISR for catalog pages.
- **NestJS**: `@nestjs/microservices` (Kafka transport), `@nestjs/typeorm` or Prisma (decide in Tech-Stack doc), `@nestjs/jwt`.
- **Kafka**: `kafkajs` client; single broker in dev/prod v1 (see Risks).
- **Redis**: `ioredis` + `@nestjs/cache-manager`.
- **ORM**: Prisma (recommended) or TypeORM — final decision recorded in `DOCS/2.Tech-Stack.md`.
- **PostgreSQL**: `postgres:16`; **MongoDB**: Atlas M0 (free); **Redis**: `redis:7` container on EC2.

### 4.3 Nginx Responsibilities
- Route `storefront.example.com` → Next.js storefront (port 3000).
- Route `admin.example.com` → Next.js admin (port 3001).
- Route `api.example.com/api/v1/*` → NestJS services by path prefix (e.g. `/auth`, `/catalog`, `/cart`, `/order`, `/cms`, `/search`).
- TLS termination (Let's Encrypt), gzip, static caching, rate limiting per IP.

## 6. Services & Responsibilities

| # | Service | Port | Responsibility |
|---|---|---|---|
| 1 | **auth-svc** | 4010 | Register/login/logout, JWT + refresh tokens, RBAC, user profile |
| 2 | **catalog-svc** | 4020 | Products, categories, brands, variants, inventory, search (basic), compare data |
| 3 | **cart-svc** | 4030 | Cart (guest + user), wishlist, cart TTL/abandonment detection input |
| 4 | **order-svc** | 4040 | Checkout, POS-style order creation, payment capture (mock provider v1), order lifecycle, stock reservation |
| 5 | **cms-svc** | 4050 | CMS sections/settings (global + per-section), theme config, navigation/megamenu config, blogs, dynamic content |
| 6 | **analytics-svc** | 4060 | Page-view events, exit tracking, abandoned cart aggregation, basic dashboards |
| 7 | **import-svc** | 4070 | Product import (CSV/JSON v1; Shopify/BigCommerce/Odoo later), validation, event publishing |
| 8 | **notify-svc** | 4080 | Email/SMS notifications (order confirmation, abandoned cart, welcome) — SMTP v1 |
| 9 | **search-svc** | 4090 | Unified search index (products, categories, blogs) synced via Kafka events; typeahead suggest + ranked full search |

Each service has its own database schema ownership (see `DOCS/3.Database-Schema.md`); cross-service reads happen via events or API, not shared tables.

## 7. Key Event-Driven Flows (Kafka Topics)

| Topic | Producer(s) | Consumers | Purpose |
|---|---|---|---|
| `cart.updated` | cart-svc | analytics-svc, notify-svc | Track cart activity; feed abandoned-cart detection |
| `cart.abandoned` | analytics-svc (detector) | notify-svc | Trigger reminder email after inactivity window (e.g. 24h) |
| `order.created` | order-svc | catalog-svc (stock), analytics-svc, notify-svc | Stock decrement, analytics, confirmation email |
| `order.status.updated` | order-svc | notify-svc, storefront (via API) | Shipment/status updates |
| `product.imported` | import-svc | catalog-svc, cms-svc, search-svc | Ingest imported products; refresh CMS caches + search index |
| `product.updated` | catalog-svc | search-svc | Admin product edits keep the search index fresh |
| `category.updated` | catalog-svc | search-svc, cms-svc | Category renames/visibility → search + navbar |
| `blog.updated` | cms-svc | search-svc | Blog create/publish/edit → search index |
| `page.viewed` | storefront (producer) | analytics-svc | Anonymous + logged-in page views, exit tracking |
| `user.registered` | auth-svc | analytics-svc, notify-svc | Welcome email, cohort analytics |

**Abandoned cart flow (v1):** storefront emits `cart.updated` → cart-svc persists cart with `updated_at` → analytics-svc runs a scheduled consumer that marks carts idle > X hours → publishes `cart.abandoned` → notify-svc sends email. (Implementation details in `DOCS/1.Architecture.md`.)

**Exit tracking (v1):** storefront fires `page.viewed` with `{userId?, sessionId, page, referrer, timestamp, device}` and a `page.left` heartbeat on `beforeunload`/`visibilitychange` → analytics-svc builds "where users leave" reports.

## 11. Budget & Deployment Strategy

### 11.1 AWS Free Tier (12 months) + $100 Credits
| Resource | Plan | Est. Monthly Cost |
|---|---|---|
| EC2 t3.micro/t4g.micro (1–2 instances) | Docker Compose: services, Kafka (self-hosted), Redis, Nginx | $0 (free tier) / ~$15 if both |
| RDS Postgres db.t4g.micro | Main relational DB | $0 (free tier 12 mo) |
| S3 | Product images, static assets | ~$0–1 |
| CloudFront (optional) | CDN for images | ~$0–2 |
| MongoDB Atlas M0 | Free cluster (shared) | $0 |
| Kafka | **Self-hosted on EC2** (MSK is ~$100+/mo — excluded) | $0 |
| Let's Encrypt | TLS certs | $0 |
| **Total** | | **$0–20/mo** |

The $100 credits are a buffer for burst usage (extra EC2, egress, RDS after free tier ends). This supports **several months of free/cheap operation** — comfortably weeks, realistically months.

### 11.2 Architecture Decisions for Cost
- One EC2 box v1: Docker Compose runs all NestJS services + Kafka (single broker) + Redis + Nginx + two Next.js apps.
- No MSK, no ECS Fargate, no ElastiCache — all self-hosted on EC2.
- RDS Postgres (managed, free tier) rather than Postgres on EC2 — one managed component for reliability.
- Images on S3, served via Nginx/CDN.

### 11.3 Deploy Pipeline
GitHub → (GitHub Actions, later phase) → build Docker images → push to ECR/GHCR → pull on EC2 → `docker compose up`. Manual `docker compose` deploy acceptable for v1.

## 13. Risks & Constraints

| Risk | Mitigation |
|---|---|
| Single-broker Kafka on t3.micro = no HA, limited RAM | Acceptable for learning; document limits; use KRaft mode (no Zookeeper) to save RAM |
| t3.micro (1 vCPU / 1GB RAM) is tight for 9 services + Kafka + Redis + 2 Next.js | Use t3.small/medium while free-tier-adjacent or offset with $100 credits; tune Node heap sizes; consider merging analytics into an EC2 instance |
| Free tier ends after 12 months | Keep costs < $20/mo; $100 credits buffer; postgres snapshot/backup plan |
| MongoDB Atlas M0 limits (512MB, no backups) | Only CMS documents; Postgres remains source of truth for critical data |
| Guest cart persistence across devices | Session-scoped carts v1; merge on login |
| CMS settings explosion → slow storefront | Redis caching with invalidation on `cms.updated` events |
| Kafka events lost on restart (no replication) | Consumer idempotency design (order/cart events carry idempotency keys) |
