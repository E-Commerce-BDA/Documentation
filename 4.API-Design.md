## 1. API Conventions (global rules)

### 1.1 Base Path & Versioning
- All APIs: `https://api.example.com/api/v1/{route}/*` — routed by Nginx to services (§2).
- Path versioning (`/v1/`) — simplest, cache-friendly; breaking changes bump to `/v2/`.

### 1.2 Authentication Headers
| Header | Where | Value |
|---|---|---|
| `Authorization: Bearer <accessToken>` | storefront/admin → API | Customer or admin JWT (15m) |
| `x-service-key` | service → service | Static internal key per service (v1) |
| `x-request-id` | everywhere | UUID generated at Nginx; echoed in responses + logs |
| `x-idempotency-key` | checkout, cart mutations | UUID from client — dedupe guard (§1.7) |

> The gateway verifies the token and strips forged identity headers. Services
> with role-sensitive routes re-verify the JWT and enforce the required
> role/permission; `x-roles` is never trusted. Identity-only routes may use
> the gateway's trusted `x-user-id` on the private path.

### 1.3 Pagination
| Context | Strategy | Params | Response |
|---|---|---|---|
| Storefront lists (products, orders, blogs) | **Cursor** | `?cursor=base64(createdAt_uuid)` + `?limit=24` | `{ data: [...], nextCursor: "..." }` — stable under inserts, no offset drift |
| Admin tables | **Offset** | `?page=1&perPage=25` | `{ data: [...], page, perPage, total }` |

Cursor encoding: `base64("<createdAtISO>|<id>")` — lexicographically sortable; `nextCursor: null` = no more pages.

### 1.4 Filtering & Sorting (storefront lists)
- Filters: `?category={slug}`, `?brand={slug}`, `?minPrice=10&maxPrice=100`, `?tag=summer`, `?q=keyword` (search), `?discounted=true`
- Sort: `?sort=price.asc | price.desc | newest | rating` (default `newest`)
- Compare: `?ids=uuid1,uuid2` (max 4)

### 1.5 Error Envelope
```json
{
  "error": {
    "code": "PRODUCT_NOT_FOUND",
    "message": "Product with slug 'x' does not exist",
    "details": [{ "field": "price", "message": "must be >= 0" }]
  },
  "requestId": "5f2c...",
  "timestamp": "2026-08-16T10:00:00Z"
}
```

| Status | Meaning |
|---|---|
| 400 | Validation error (`VALIDATION_FAILED`) |
| 401 | Missing/invalid token (`UNAUTHENTICATED`) |
| 403 | Role insufficient (`FORBIDDEN`) |
| 404 | Not found (`*_NOT_FOUND`) |
| 409 | Conflict — duplicate/invalid state (`DUPLICATE_SKU`, `STOCK_INSUFFICIENT`, `IDEMPOTENCY_CONFLICT`) |
| 422 | Semantic failure (`COUPON_EXPIRED`, `COUPON_USED`) |
| 429 | Rate limited (`RATE_LIMITED`) |
| 500 | Unexpected (`INTERNAL_ERROR`) |
| 503 | Dependency unavailable (`SERVICE_UNAVAILABLE`) |

Cart settings add three specific codes: `UNKNOWN_SETTING` (400), `INVALID_SETTING_VALUE` (400), and `SETTINGS_VERSION_CONFLICT` (409, with the current version in `details`).

Health/readiness responses are the one exception: probes parse status, not envelopes, so they carry only `status`/`checks` (see §1.9).

### 1.6 Rate Limits (Nginx, per IP)
| Group | Limit |
|---|---|
| `/api/v1/auth/login`, `/api/v1/auth/refresh` | 10 req/s |
| `/api/v1/order/checkout` | 5 req/s |
| `/api/v1/cart/settings` | 5 req/s (admin; writes 2/s) |
| `/api/v1/analytics/events/*` | 30 req/s |
| All reads | 30 req/s per route |

### 1.7 Idempotency
- `x-idempotency-key` **required** on `POST /order/checkout`, `POST /cart/items`, `PATCH /cart/items/:id`, `DELETE /cart/items/:id`, `DELETE /cart/items`, `DELETE /cart`, and `POST /cart/merge`. UUID v4 from the client.
- **Key scope is `(user, route, key)`, never the bare key.** The server-side key is `idem:{userId}:{route}:{key}`, so two customers who happen to generate the same UUID can never replay each other's response.
- **The domain row is the authority; Redis is a replay cache.** On checkout the key is persisted on the order itself — `orders.idempotency_key` + `orders.idempotency_body_hash`, gated by a partial unique index on `(user_id, idempotency_key)` — and the Redis map (`idem:…`, 24h TTL) only short-circuits the round trip. A cache hit with no matching DB row (a restored dump, an eviction) is treated as a miss and re-derived from the database, so the cache can never invent an order.
- Replaying a key with the **same** body returns the stored response (`201`, identical `orderId`/`orderNumber`, exactly one order). Replaying it with a **different** body → `409 IDEMPOTENCY_CONFLICT`. A key whose attempt already ended in `failed`/`cancelled` → `409 ORDER_ATTEMPT_CLOSED` (the key is burned; a new attempt needs a new key). A key currently executing → `409 IDEMPOTENCY_IN_PROGRESS`.
- **Fail closed only before the first durable write.** If Redis is unreachable *before* anything is persisted, checkout returns `503 IDEMPOTENCY_UNAVAILABLE` (nothing happened, safe to retry with the same key). A Redis failure *after* the order commits is logged and the `201` still stands — the client's retry replays from the DB instead of being told a real order failed.
- The concurrent-duplicate case is settled by the unique index, not by the lock: two requests carrying the same key race to one insert, the loser gets a unique violation and is served the winner's confirmation (its own capture and stock hold are compensated).
- `POST /cart/merge` is naturally idempotent because the guest cart is consumed; the key still gives exact response replay.
- Admin `PATCH /cart/settings` is **not** keyed — its `version` field is the concurrency guard.

### 1.8 Contract-First & OpenAPI (via `@ecom/contracts`)
- Source of truth is **`ecom-contracts` repo (`@ecom/contracts`)** — event envelopes + 10 payload schemas (`src/events/`, Kafka log), task job schemas (`src/jobs/`: `send-email`, `process-row`, `resize-image`, `reminder.dispatch`), REST DTOs, Zod `cta.schema.ts` (`ctas[]` max 3), error codes. This doc references; services pin a version (no `^`). Breaking changes follow `8.Versioning.md` (MAJOR = dual-publish window + CHANGELOG).
- Full OpenAPI 3.1 specs generated per service **from `@ecom/contracts` DTOs** (Swagger module), exposed at `GET /api/v1/{route}/docs` and exported to `zod-to-openapi`.
- Event contracts live in `1.Architecture.md` §7 (Kafka log) + `@ecom/contracts/src/events/`; task contracts in `1.Architecture.md §6.6` + `@ecom/contracts/src/jobs/` — API doc only references them.
- Replay note: **Kafka log supports replay** (e.g. re-consume `product.imported` after search bug, 3–30d retention). SQS task queues delete on consume (14d max) — task retries come from redrive/visibility-timeout, not replay.
- SQS task hygiene: **long-poll 20s + batch 10, Standard queues** (FIFO only if per-user order ever needed) — avoids empty-receive inflation ($0.40/M Standard / $0.50/M FIFO, first 1M/mo free, 64KB chunk rule).

### 1.9 Health & Readiness (every service)

Two probes, both **outside `/api/v1`** and outside the §1.5 envelope. Probes are exempt from §1.6 rate limits — a load balancer polls continuously and a per-IP cap would evict it.

| Endpoint | Checks deps | `200` | Failure | Caller |
|---|---|---|---|---|
| `GET /health` | **never** | `{"status":"ok"}` | never fails while the process runs | Docker `HEALTHCHECK`, restart policy |
| `GET /health/ready` | Postgres (v1); Redis/bus when wired | `{"status":"ready","checks":{"db":"up"}}` | `503 {"status":"not_ready","checks":{"db":"down"}}` | Compose `depends_on`, ALB target group |

Rules:
- **Liveness never touches a dependency.** A database outage must not restart the process — a restart cannot fix a downstream outage and can cascade across services.
- **Readiness answers `503`, not `500`.** "A dependency is unavailable" is a routing decision, not an application error; the LB stops sending traffic without firing a crash alarm.
- **Bodies stay minimal.** No driver messages, DSNs, or stack traces; the real error goes to the service log.
- **Bounded.** Readiness must answer within the service's probe budget (the pool connect/query timeouts), never hang.
- Ops usage (alarms, restart policy, dashboards): `10.Observability.md §3`.

## 2. Nginx → Service Routing Map

```mermaid
flowchart LR
    C[Client] -->|https api.example.com/api/v1| N[Nginx]
    N -->|/api/v1/auth/*| S1[auth-svc :4010]
    N -->|/api/v1/catalog/*| S2[catalog-svc :4020]
    N -->|/api/v1/cart/*| S3[cart-svc :4030]
    N -->|/api/v1/order/*| S4[order-svc :4040]
    N -->|/api/v1/cms/*| S5[cms-svc :4050]
    N -->|/api/v1/analytics/*| S6[analytics-svc :4060]
    N -->|/api/v1/import/*| S7[import-svc :4070]
    N -->|/api/v1/notify/*| S8[notify-svc :4080]
    N -->|/api/v1/search/*| S9[search-svc :4090]
    B[Browser sendBeacon] -->|POST /api/track| NW[Next.js storefront route]
    NW -->|server-side forward x-service-key| N
```

`proxy_pass` has **no trailing slash**: the gateway forwards the path unchanged, so each service owns its `/api/v1` prefix (§1.1) and a local `curl` hits the same URL as production.

### 4.6 `POST /order/checkout` (idempotent)
Header: `x-idempotency-key: 5f2c...`
**Request**
```json
{
  "items": [{ "productId": "0190...", "variantId": "var1", "qty": 2 }],
  "shippingAddress": { "line1": "...", "city": "...", "postalCode": "...", "country": "US" },
  "billingAddress": { "line1": "...", "city": "...", "postalCode": "...", "country": "US" },
  "discountCode": "SAVE10",
  "payment": { "provider": "mock" }
}
```
**Response `201`**
```json
{
  "orderId": "0190...", "orderNumber": "#2026-000123", "status": "confirmed",
  "totals": { "subtotal": 159.98, "shipping": 5.0, "tax": 9.9, "discount": 15.99, "grandTotal": 158.89 },
  "items": [{ "productName": "Running Shoe X", "sku": "RSX-100", "unitPrice": 79.99, "qty": 2, "lineTotal": 159.98 }]
}
```
**Emits:** `order.created` via **transactional outbox** (same TX that flips the pending row to `confirmed`). **Replay:** same key → the stored confirmation, byte for byte.

**The order is persisted before the money moves.** `201` means the order exists, is `confirmed` and is paid — never a promise: the row is inserted as `pending` first, the capture runs against that `orderId`, and only then is it confirmed (§5.1). A `pending` order therefore only survives when the attempt was interrupted, and retrying with the same key resumes it.

| Status | `code` | When | Client action |
|---|---|---|---|
| `400` | `VALIDATION_FAILED` | body fails the DTO | fix the body |
| `402` | `PAYMENT_FAILED` | the provider declined the card | new key, new attempt (the key is burned) |
| `409` | `STOCK_INSUFFICIENT` / `RESERVATION_CLOSED` / `RESERVATION_CONFLICT` | the hold could not be taken | refresh the cart |
| `409` | `IDEMPOTENCY_CONFLICT` | same key, different body | new key |
| `409` | `IDEMPOTENCY_IN_PROGRESS` | the same key is executing right now | retry shortly |
| `409` | `ORDER_ATTEMPT_CLOSED` | the key's attempt already ended `failed`/`cancelled` | new key |
| `422` | `COUPON_EXPIRED` / `COUPON_USED` | the coupon is not redeemable | drop the coupon |
| `502` | `CATALOG_CONTRACT_ERROR` | catalog rejected our body (deploy skew) | page the platform team |
| `503` | `CATALOG_UNAVAILABLE` / `IDEMPOTENCY_UNAVAILABLE` | dependency down **before** anything was written | retry with the same key |
| `503` | `PAYMENT_UNAVAILABLE` | the provider could not be reached; the order stays `pending` | retry with the same key (resumes) |
| `503` | `CHECKOUT_UNAVAILABLE` / `PAYMENT_PERSIST_FAILED` | the write failed after stock was held (a capture is refunded first) | retry with the same key |

### 4.14 `POST /order/orders/:id/refund` (admin)
`{ "amount": 118.00, "reason": "Customer returned item" }` — `amount` defaults to `grand_total` and may not exceed it (`400`).

**Response `200`**
```json
{
  "order": { "id": "0190...", "status": "refunded", "payment_status": "refunded" },
  "refund": {
    "id": "0191...", "order_id": "0190...", "payment_id": "0192...",
    "amount": "118.00", "status": "succeeded", "provider_reference": "mock_ref_...",
    "failure_reason": null, "reason": "Customer returned item", "requested_by": "admin-1"
  }
}
```

**Flow.** The refund row is reserved (`pending`) *before* the provider is called and settled only after it answers, so the response is the provider's result and not our intention:

1. `refunds` row exists? `succeeded` ⇒ return it as-is; `pending` ⇒ `409 REFUND_IN_PROGRESS`; `failed` ⇒ retry in place with the reserved amount.
2. Pick the captured payment (`status='captured'`, `transaction_id NOT NULL`) — the refund is issued against *that* transaction id, never the order id.
3. `INSERT` the refund row: `UNIQUE (order_id)` settles a concurrent double-click, the loser reads the winner's row.
4. `processRefund(transaction_id, amount, reason)`; on success one transaction writes `refunds→succeeded` + `provider_reference`, `payments→refunded`, `orders→refunded/refunded`, the history row and the canonical `order.status.updated` outbox event.

**Errors:** `400` amount above `grand_total` or an illegal FSM transition, `403` non-admin, `404` unknown order, `409 NO_CAPTURED_PAYMENT` (nothing was ever captured — e.g. a `pending`/`failed` order), `409 REFUND_IN_PROGRESS`, `502 REFUND_PROVIDER_FAILED` (the provider refused or was unreachable; the refund row is `failed` with the reason, the order and payment are untouched and a retry reuses the same row).

## 5. Critical Flow Sequences

### 5.1 Checkout (idempotency + pending-first saga + outbox)
```mermaid
sequenceDiagram
    participant SF as Storefront
    participant OR as order-svc
    participant RD as Redis
    participant CAT as catalog-svc
    participant PAY as Payment provider
    participant DB as Postgres (order + outbox)
    participant K as Kafka

    SF->>OR: POST /checkout (x-idempotency-key: K1)
    OR->>RD: GET idem:{userId}:checkout:K1
    Note over OR,RD: miss or unparseable ⇒ continue<br/>hit + same body hash ⇒ replay the stored 201<br/>hit + other hash ⇒ 409 IDEMPOTENCY_CONFLICT<br/>Redis error ⇒ 503 IDEMPOTENCY_UNAVAILABLE
    OR->>RD: SET idem:…:lock NX EX 60
    OR->>DB: SELECT order WHERE (user_id, idempotency_key)
    Note over OR,DB: confirmed ⇒ replay the confirmation<br/>pending ⇒ resume (re-capture, same order id)<br/>failed/cancelled ⇒ 409 ORDER_ATTEMPT_CLOSED
    OR->>CAT: POST /catalog/internal/stock/reserve (reservationId, items)
    CAT-->>OR: 201 { reservationId, expiresAt, items[] }
    OR->>OR: validate coupon, clamp discount, snapshot prices
    OR->>DB: TX1 — order status=pending, items, history, payment pending, key + body hash
    OR->>PAY: capture(grandTotal, orderId)
    PAY-->>OR: transactionId
    OR->>DB: TX2 — payment captured, order confirmed/paid, history, outbox order.created
    OR->>RD: SET idem:{userId}:checkout:K1 (24h) — a failure here is only a warning
    OR->>RD: DEL …:lock
    OR-->>SF: 201 order
    K->>DB: relay polls idx_outbox_pending → publish order.created
```

The reservation id is generated by order-svc before the call and is catalog's idempotency key, so a retried checkout cannot decrement stock twice. Failures map to distinct statuses so the storefront knows whether to blame the cart or the platform: `409` (`STOCK_INSUFFICIENT` / `RESERVATION_CLOSED` / `RESERVATION_CONFLICT`), `502 CATALOG_CONTRACT_ERROR` (the client sent a body catalog rejected — a deploy-skew bug, not a customer problem) and `503 CATALOG_UNAVAILABLE` (network/5xx/timeout; safe to retry with the same idempotency key). The hold stays `held` until `cat-009` commits it from `order.created`.

**Why TX1 comes first.** Money must never exist without an order, so the order row is the first durable write: a `pending` row plus a `pending` payment is the promise, then the capture, then the confirmation. The hold is taken before TX1 because a pending order with no hold could be confirmed against stock nobody reserved.

**Compensation, one path per failure point:**

| Failure | What is rolled back | Response |
|---|---|---|
| reserve / snapshot / coupon | the hold, if it was already taken | `409` / `422` / `502` / `503` (unchanged) |
| TX1 | the hold | `503 CHECKOUT_UNAVAILABLE` |
| capture declined | attempt closed `failed`, payment `failed`, hold released | `402 PAYMENT_FAILED` |
| capture threw (provider unreachable) | nothing — the order stays `pending` so a retry resumes it | `503 PAYMENT_UNAVAILABLE` |
| TX2, after a successful capture | provider refund of the capture, attempt closed `refunded`, hold released | `503 PAYMENT_PERSIST_FAILED` |

Every path releases the hold at most once; `catalog`'s release is idempotent server-side, so a retry cannot inflate stock.

| order-svc | catalog-svc | `POST /internal/stock/reserve` | Hold stock at checkout; idempotent on the caller-supplied `reservationId` |
| order-svc | catalog-svc | `POST /internal/stock/commit` | Consume the hold once the order row is committed |
| order-svc | catalog-svc | `POST /internal/stock/release` | Compensation when the checkout transaction rolls back |

| cart-svc | catalog-svc | `GET /internal/products?ids=` | Cart render enrichment (names, images) |

| storefront | search-svc | `GET /api/v1/search/suggest`, `GET /api/v1/search` | Typeahead dropdown + full search page |
| search-svc | — (Kafka events only) | consumes `product.imported` / `product.updated` / `category.updated` / `blog.updated` | Index sync — no REST deps; replay the log after a search bug |

> Internal endpoints live under the owning service's prefix — `/cart/internal/*`, `/catalog/internal/*`, `/search/internal/*`, `/auth/internal/*` — and are not exposed through Nginx public routing. Every one of them authenticates with `x-service-key` against `INTERNAL_SERVICE_KEY` and answers `401 SERVICE_KEY_INVALID` otherwise; cart-svc refuses to boot in production without a real key.

### 7.1 Stock reservation contract

`ReservationId` is a caller-supplied UUID and doubles as the idempotency key:
the same body replayed returns the stored 201 body without decrementing twice
(including concurrent replays, which block on the primary-key index entry).

```jsonc
// POST /internal/stock/reserve  → 201
{
  "reservationId": "uuid",
  "orderId": "uuid",              // optional
  "items": [{ "productId": "uuid", "variantId": "uuid|null", "quantity": 2 }]
}
// 201
{
  "reservationId": "uuid",
  "status": "held",
  "expiresAt": "ISO-8601",
  "items": [{ "productId": "uuid", "variantId": null, "quantity": 2, "remainingStock": 8 }]
}
```

`POST /internal/stock/commit` takes `{ reservationId, orderId? }` and returns
`{ reservationId, status: "committed", orderId }`; it never moves stock, because
the hold already did. `POST /internal/stock/release` restores exactly the items
stored on the hold and is a no-op when replayed. Holds that are never committed
expire after `STOCK_RESERVATION_TTL_SECONDS` (default 900) via a per-minute
sweep, which restores stock the same way a release does.

| Code | Status | Meaning | Caller action |
|---|---|---|---|
| `INSUFFICIENT_STOCK` | 409 | The hold cannot be satisfied | Reject the checkout, nothing was written |
| `RESERVATION_CLOSED` | 409 | Hold is `committed`, `released` or `expired` and cannot transition | Treat as terminal; never retry the same intent |
| `RESERVATION_CONFLICT` | 409 | Another hold already exists for this `orderId` | Generate a new order/reservation id |
| `404` | 404 | Unknown `reservationId` | Bug in the caller — the id must be generated locally |
