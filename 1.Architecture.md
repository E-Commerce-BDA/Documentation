## 1. Architecture Principles

1. **HTTP for responses, Kafka for domain consequences, SQS for task execution.** Requests that must return a synchronous answer (fetch product, create cart item, authenticate) go over REST via Nginx. Domain consequences that other services must observe in order (stock decrement, analytics, search sync, emails triggered) are published as events on **self-hosted Kafka** through `IEventBus`. Units of work to execute (send this email, process this import row, resize this image) are enqueued on **SQS** through `ITaskQueue`. Services never import transport clients directly. Event/job envelopes come from `@ecom/contracts`.
2. **Service independence & polyrepo.** Each NestJS service lives in its own git repo and owns its data/lifecycle/pipeline; no service reads another service's DB table or imports its code — it consumes events or calls an API. Shared types/events come only from versioned `@ecom/contracts` (semver, `8.Versioning.md`).
3. **Data ownership.** Each database schema/collection is owned by exactly one service. Ownership map in `3.Database-Schema.md`.
4. **Eventual consistency by design.** Reads may lag writes by milliseconds; compensation flows handle partial failure (saga-lite).
5. **Fail-fast for user-facing commands, graceful degradation for reads.** Checkout fails loudly on validation errors; catalog falls back to cache/DB when the bus is down.
6. **Idempotency everywhere.** Every event and every task carries an idempotency key so replays/redeliveries never double-apply (no double stock decrement, no double email). Learning-scale intentionally — NOT traffic-scale (single Kafka broker, SQS Standard, no K8s/MSK/ElastiCache in v1).

## 5. Communication Patterns

| Interaction | Channel | Why |
|---|---|---|
| Storefront → auth (login, profile) | REST | Needs immediate response + token |
| Storefront → catalog (products, search, compare) | REST | Read path; SSR/ISR fetches at request time |
| Storefront → cart (add/update/remove) | REST | Immediate UI feedback; cart-svc publishes `cart.updated` async for analytics |
| Storefront → order (checkout) | REST | Returns order confirmation synchronously; order-svc then emits events |
| Admin → cms (settings, sections) | REST | Save settings; cms-svc publishes `cms.updated` for cache invalidation |
| Admin → import (CSV upload) | REST | Accepts file; import-svc publishes `product.imported` when done |
| Cross-service domain consequences (stock, analytics, search sync, email triggers) | `IEventBus` → self-hosted Kafka | Ordered per-key, replayable log; never blocks user; same broker in every environment |
| Units of work (send email, process import row, resize image, dispatch reminder) | `ITaskQueue` → SQS | Managed to-dos; Standard (FIFO only if per-user order needed); long-poll 20s + batch 10; redrive DLQ |
| Analytics ingestion | `IEventBus` → Kafka | High-volume `page.viewed` must not hit HTTP round-trips |

> Rule: response needed → REST. Domain fact other services must observe → Kafka event via `IEventBus`. Job to execute → SQS task via `ITaskQueue`. Services inject the ports (`KafkaBus` / `SqsTaskQueue`) and never import `kafkajs`/AWS SDK directly. Envelopes come from `@ecom/contracts` (`src/events/`, `src/jobs/`).

## 6. Event Log (Kafka) + Task Queues (SQS)

> Services depend on two ports: `IEventBus` (`publish(envelope)` / `subscribe(type, handler)`, impl `KafkaBus`) for domain events and `ITaskQueue` (`enqueue(job)` / `process(queue, handler)`, impl `SqsTaskQueue`) for jobs. Each workload lives on exactly one transport — events never go to SQS, tasks never go to Kafka. Schemas in `@ecom/contracts` (`src/events/`, `src/jobs/`; semver in `8.Versioning.md`).

### 6.1 Broker — Self-Hosted Kafka Event Log (every environment)

- **Single broker, KRaft mode** (no Zookeeper — saves ~250MB RAM on t3.micro). Runs in **every** compose profile (local + AWS EC2, `$0` extra).
- Kafka runs as a Docker container on the EC2 host (`kafka:3.x`).
- Auto-create disabled; topics defined declaratively in `docker-compose.yml`/provision script.

### 6.2 Envelopes (versioned in `@ecom/contracts`)
Events and tasks share the same envelope shape (type + version + idempotencyKey):

```json
{
  "id": "uuid-v4",
  "type": "order.created",
  "version": 1,
  "timestamp": "2026-08-15T10:00:00Z",
  "producer": "order-svc",
  "idempotencyKey": "order-123",
  "payload": {}
}
```

See `ecom-contracts/src/events/` for schema source of truth and `8.Versioning.md` for MAJOR/MINOR/PATCH rules (breaking changes use dual-publish window).

- One consumer group per (service, topic): e.g. `analytics-svc-cart.updated`, `catalog-svc-order.created`, `search-svc-product.updated`.
- **DLQ**: every source topic has a `.dlq` twin. A consumer that fails N times (default 5 with exponential backoff 1s→2s→4s→8s→16s) publishes the raw event to the DLQ and commits, so the group never stalls. DLQ messages are inspected manually (admin) or via a replay tool.
- **Idempotency**: consumers persist `idempotencyKey` in a processed-events table (or Redis set) and skip already-seen keys — protects against at-least-once redelivery on broker/consumer restart.

### 6.5 SQS Reference (queue mechanics for task queues — §6.6)

Task queues are provisioned via `ecom-infra/aws/` (Terraform/CDK — SQS queues + redrive DLQs + least-privilege IAM per service). No SNS fan-out needed (one queue per job type, not per consumer).

**Queue rules (apply to §6.6 task queues):**
- **DLQ:** SQS redrive policy (`maxReceiveCount 5` → DLQ queue); same 5× backoff philosophy as Kafka.
- **Type:** Standard unless per-user order is required (then FIFO with `MessageGroupId`). All four v1 task queues are Standard.
- **Polling:** always `WaitTimeSeconds 20` (long poll) + `MaxNumberOfMessages 10`; short polling silently inflates billable requests (64KB chunk rule). Billed $0.50/M FIFO / $0.40/M Standard, first 1M/mo free.
- **No replay:** SQS deletes on consume, 14d max retention (vs Kafka 3–30d + replay). Task retries come from redrive/visibility-timeout, not log rewind.
- **Idempotency:** `idempotencyKey` dedupe still required on jobs (Standard may double-deliver).

### 6.6 Task Queues (SQS — every environment)

One queue per job type (not per consumer). Schemas in `@ecom/contracts/src/jobs/`.

| Task queue | Producer(s) | Consumer | Purpose |
|---|---|---|---|
| `notify.send-email` | notify-svc (from `order.created`, `cart.abandoned`, `user.registered`) | notify-svc worker | SMTP sends with retry; email log per attempt |
| `import.process-row` | import-svc (from CSV/JSON upload) | import-svc worker | Per-row validation → `product.imported` event on Kafka |
| `media.resize-image` | cms-svc / catalog-svc (from uploads) | media worker | Thumbnails/variants off the request path |
| `reminder.dispatch` | analytics-svc detector (from idle carts) | notify-svc worker | Schedules the reminder that `cart.abandoned` announces |

Flow example: `order-svc` → Kafka `order.created` → `notify-svc` consumes → enqueues `notify.send-email` (SQS) → worker sends SMTP → writes `notify.email_logs` (Postgres).

Key directives planned:
- **Server blocks**: one per domain (storefront, admin, api) with dedicated upstreams.
- **Path-prefix routing**: `api.example.com` routes by first path segment to the right service.
- **Rate limiting**: `limit_req_zone` keyed by IP for `/api/auth` (e.g. 10 req/s) and `/api/order` (e.g. 5 req/s) to blunt brute-force/abuse.
- **Static caching**: `/static/*` and image proxies with `Cache-Control`, immutable for hashed assets.
- **gzip**: on for text content; off for images/PDFs.
- **TLS**: certbot + auto-renew cron; HSTS header.
- **Client body size**: raised (e.g. 25m) for product image uploads via admin.

## 9. Auth & Security

```mermaid
sequenceDiagram
    participant U as Customer
    participant N as Nginx
    participant A as auth-svc
    participant S as Services (API)

    U->>N: POST /api/auth/login
    N->>A: forward
    A->>A: verify credentials
    A-->>U: { accessToken, refreshToken }
    U->>N: GET /api/cart with Bearer accessToken
    N->>S: forward (accessToken in header)
    S->>S: verify JWT (shared secret)
    S-->>U: response
    U->>A: POST /api/auth/refresh (refreshToken)
    A-->>U: new accessToken
```

- **JWT**: HS256 access token (short, e.g. 15m) + refresh token (30d, rotated, stored hashed in `auth` schema).
- **RBAC**: roles `customer` / `admin`; admin routes gated by a `RolesGuard` in the admin app and by role claim in JWT on API.
- **Service-to-service**: internal static API keys in v1 (header `x-service-key`) checked by each service; replaced by mTLS/IAM in later phases.
- **CORS**: allowlist storefront + admin origins on the API domain.
- **Secrets**: `.env` files on EC2 (chmod 600) + AWS Secrets Manager as the v2 upgrade path. No secrets committed to git.

## 10. Data Consistency Patterns

### 10.1 Transactional Outbox (order-svc)
Order creation and the outbox insert happen in the **same DB transaction**. A relay worker (in-process poller or Debezium later) reads `outbox` and publishes `order.created` → guarantees no order without its event, no event without its order.

### 10.2 Idempotency Keys
Every event and every task carries `idempotencyKey`; consumers/workers dedupe via a processed-keys table/Redis set. Protects against at-least-once redelivery on broker/queue/consumer restart.

### 10.3 Saga-Lite Order Flow (with compensation)

```mermaid
sequenceDiagram
    participant SF as Storefront
    participant OR as order-svc
    participant DB as Postgres (outbox)
    participant K as Kafka (event log)
    participant Q as SQS (task queues)
    participant CA as catalog-svc
    participant NT as notify-svc
    participant AN as analytics-svc

    SF->>OR: POST /checkout
    OR->>OR: validate cart + payment (mock)
    OR->>DB: TX(insert order + insert outbox)
    OR-->>SF: order confirmation (id)
    DB-->>OR: outbox row
    OR->>K: publish order.created
    K->>CA: consume → decrement stock
    K->>NT: consume → enqueue notify.send-email
    NT->>Q: send-email task
    Q->>NT: worker sends SMTP → email_logs
    K->>AN: consume → record conversion
    CA-->>OR: stock reservation failed → order-svc marks order failed (compensation)
    OR->>K: publish order.status.updated (failed)
```

- On stock reservation failure, order-svc marks the order `failed` and emits `order.status.updated` so the customer is notified and funds (mock) are released.

## 11. Caching Strategy (Redis)

```mermaid
flowchart LR
    REQ[Request] --> CACHE{In Redis?}
    CACHE -->|yes| HIT[Return cached]
    CACHE -->|no| MISS[Read DB]
    MISS --> SET[Write cache + TTL]
    SET --> HIT

    EVT[product.imported / cms.updated] --> INV[Invalidate keys]
    INV --> CACHE
```

- **Cache-aside** for catalog reads and CMS settings; TTLs: catalog 5m, CMS global 1m, per-section 5m.
- **Keyspace**: `cat:product:{id}`, `cat:list:{queryHash}`, `cms:section:{key}`, `cms:settings:global`, `sess:{tokenId}`.
- **Invalidation**: consumers of `product.imported` and `cms.updated` delete affected keys.
- **Sessions**: refresh-token sessions in Redis with sliding TTL.
- **Rate limiting**: Redis-backed counters for Nginx-auth and checkout endpoints.

## 12. Deployment Topology (EC2 + Docker Compose — Learning-Scale)

## 13. Resilience & Failure Handling

| Failure | Handling |
|---|---|
| Kafka broker down | Event consumers block with backoff; order-svc writes events to local outbox (DB) so nothing is lost; storefront reads unaffected (reads are HTTP/Redis). |
| SQS throttled or unavailable (task queues) | `SqsTaskQueue` retries with backoff; jobs stay visible after visibility-timeout; CloudWatch alarm on `ApproximateAgeOfOldestMessage` / `ApproximateNumberOfMessagesVisible`. |
| Consumer crash mid-batch | At-least-once delivery + idempotency keys dedupe replays (Kafka and SQS Standard both at-least-once). |
| Poison message / poison task | Retry 5× with exponential backoff, then route to DLQ (Kafka `.dlq` topic / SQS redrive `maxReceiveCount 5` → DLQ queue); group/queue never stalls. |
| Redis down | Catalog falls back to DB; sessions degrade to DB lookup; rate limiting bypassed (documented, v1 acceptable). |
| RDS down | Read replicas (traffic-scale); backups daily with 7-day retention + S3 snapshot before Free Plan expiry (v1). |
| Payment provider (mock) down | Checkout returns clear error; order not created. |
| EC2 restart | `docker compose` `restart: unless-stopped`; outbox replay after boot; Kafka log replays from retained offsets; SQS task backlog survives up to 14d. |

## 14. Observability

- **Structured JSON logs** per service (pino/winston) to stdout → Docker logs → CloudWatch Logs on AWS.
- **Health endpoints**: `GET /health` (liveness) + `/health/ready` (deps) on every service → ALB/Compose health checks + CloudWatch alarms (5xx, P99, billing 50/25/10%).
- **Request IDs**: `x-request-id` generated at Nginx, propagated via headers, logged in every service.
- **Transport metrics**: Kafka consumer lag via `kafka-consumer-groups.sh` (cron) and admin endpoint; SQS task queues via `ApproximateAgeOfOldestMessage` / `ApproximateNumberOfMessagesVisible` / `NumberOfMessagesDelayed` alarms + DLQ depth.
- **Prometheus + Grafana**: traffic-scale goal (annotations now, exporters later). No paid APM in v1 (budget).
